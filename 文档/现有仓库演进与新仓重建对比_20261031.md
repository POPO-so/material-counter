# 现有仓库演进与新仓重建：实现难度评估

- 日期：2026-10-31，北京时间。
- 评估目标：落实[架构问答整理](PYNQ-Z2螺母视觉计数系统_问题与架构评审_20261031.md)中的推荐，比较现仓库演进与另建仓库。
- 方法：一名 `luna_explorer` 只读查阅索引、实际入口、PS/PL 源码和边界记录；Manager 复核关键源码与文档，并审阅最终文件。
- 验证等级：静态源码及历史证据核查；没有执行软件回归、RTL 仿真、综合、板端运行或物料准确率测试。
- 基线：从 `LJ-01` 的 `54e6c79` 开始本轮文档整理。下列引用对应这一轮核查的工作区，不把计划文档当实现证明。

## 1. 结论

**更容易实现的是：保留现有仓库，在独立开发分支上建立清楚的模块边界，逐步替换。**

这是一项基于现有资产和迁移范围的工程判断，不是已通过实验量化的工期比较。现仓库已经解决不少与算法无关但很费时间的问题：USB 原尺寸灰度采集、DMA/overlay 适配、RLE 与 PS 原生连通域、HDMI 输出、资源所有权、故障收尾、制品身份与回放素材。新仓库不会自动消除相机吞吐、物理可观测性、身份去重和接口决策问题，却需要重新整合或搬迁这些资产。

建议形成**同仓的下一代候选入口和稳定接口**，让新旧前端可对照；不要为追求干净目录立即重写整个系统，也不要把所有推荐一次性塞进当前大类。独立分支用于开发隔离；可保留独立候选入口进行长期比较，验证后按项目规则合并。

## 3. 两条路径的实现难度

| 维度 | A：现仓库渐进演进 | B：另建仓库 |
|---|---|---|
| USB/Gray8 输入 | 复用后按新边界调整 | 搬迁或重新实现，并核对驱动环境 |
| Vivado 工程/约束/视频 IP | 在已知板级工程上增量接入 | 搬迁依赖、路径、版本锁及构建脚本 |
| DMA 与缓存所有权 | 复用保护框架，修改 ABI | 重新整合分配、等待、缓存和清理 |
| 跟踪架构 | 需抽离当前耦合；可同输入对照 | 可以直接设计干净接口，但身份问题仍要重验 |
| PL CCL/Overlay/编码器 | 仍需新增，现有骨架可承接 | 同样需新增，还需先补齐骨架 |
| 回归素材 | 保留历史和来源关系 | 必须迁移、修复引用与重建来源关系 |
| 部署连续性 | 可保留候选、回退与唯一 owner 机制 | 新旧部署、包身份和运行者所有权更复杂 |
| 文档负担 | 需要梳理重复入口与候选状态 | 初期目录干净，但大量事实、证据、依赖需迁移 |
| 风险隔离 | 独立分支/工作树/候选入口即可实现 | 仓库隔离更彻底，但不能隔离同一块板上的硬件冲突 |
| 综合判断 | **较容易，推荐** | 只有独立产品/技术栈等明确边界时更有价值 |

“新仓库”与“新架构”不是同一件事。新架构可以在现仓库中逐模块替换；复制旧代码到新仓库也不会自然获得低耦合。

## 4. 按上一轮每部分推荐，具体怎样落地

| 上轮部分 | 在现基础上的落实方式 | 优先级/注意点 |
|---|---|---|
| 1 硬件事实 | 复用参数资料和现有采集基准，补真实枚举、曝光与时间戳证据 | 最先；硬件升级不得建立在标称 FPS 上 |
| 2 算法比较 | 用现有 synth/真实样本对比轨迹、TSI、分道等候选，不先改硬件 | 先确定可观测信息 |
| 3 去重逻辑 | 先定义通行事件，抽出 Detection→Tracker→Event 接口；保留旧行为对照，再逐项引入 U/G/D 和身份恢复 | 准确性核心；不能当作改几个状态名 |
| 4 数据流 | 保留 USB/Gray8/DMA，先去掉不必要复制和串行等待；新 ABI 在单独入口验证 | 先测阶段耗时再决定下沉收益 |
| 5 分工通信 | RLE＋PS 原生 CCL 作过渡；先稳定语义，再实现有界 PL CCL/特征包 | 完整 PL CCL 是新增高风险模块 |
| 6 HDMI | 复用 HDMI 与 PS 绘图，先确保帧配对和独立运行；有带宽证据后加 PL Overlay | 不抢在准确性和输入瓶颈前 |
| 7 监控 | 复用 Linux 采样和 RLE 计数器，统一快照、帧号和口径 | 不将 HP 统计冒充 DDR 总利用率 |
| 8 性能预算 | 使用理论表作预算，用采集/解码/DMA/CCL/跟踪/绘图分位耗时定位瓶颈 | 高 FPS、资源和准确率均待实测 |
| 9 总体架构 | 同仓候选入口组合已验证模块；数据 ABI/绘图接口版本化 | 按项目规则形成决策，不自动冻结 |
| 10 路线验收 | 优先物理真值和去重，再有依据地迁移 C++/PL、编码器与显示 | 重新验收修改所影响的范围 |

上一轮十个章节是论证顺序，不应机械理解成十次代码改动。**PL full CCL、全量 C++ 跟踪、PL Overlay、编码器**也不应在未测收益时同时开工：它们分别是可分阶段验证的工作，不是达到首个可靠计数版本的必然前置条件。

## 5. 推荐实施顺序

1. 保存可追溯基线，明确当前候选入口、位流和配置；保持既有证据的版本边界。
2. 核实相机有效成像与整链各段耗时；建立含粘连、倒退、停顿、丢帧的真值集。
3. 抽出稳定的检测结果与事件接口。先用当前 RLE＋PS 原生 CCL 喂新 tracker，不同时更换全部前端。
4. 实现 U/G/D、事件幂等、丢失恢复与已计数身份保持，进行新旧同输入比较。CPU 迁移需要独立验证，不凭语言选择推定提速。
5. 按实测瓶颈选择是否把 CCL 下沉 PL。新特征 ABI、容量保护和局部分离数据入口一同设计。
6. 对变速/倒退需求单独接入编码器，核实电气、时间同步和滑移；不能用软件时间戳冒充已接入编码器。
7. 沿用 HDMI 骨架，先保证同帧配对与计数隔离，再按资源/带宽证据加入 PL Overlay。
8. 汇总遥测、更新候选包和文档，执行所影响范围的验收；正式签署/冻结由项目既定机制决定。

本轮仅交付上述建议，没有开始这八步的工程修改，没有新建其他仓库。是否改变正式架构及受保护接口需要后续独立设计与决策，本文不代替它们。

## 6. 什么时候才考虑另建仓库

- 明确要形成独立产品，使用不同板卡、技术栈或维护/发布生命周期。
- 原仓库依赖或许可确实妨碍复用，并已有证据表明同仓模块隔离无法解决。
- 已完成边界清楚的重写/提取，可连同源码来源、依赖、测试和部署说明迁移，不以切断历史回避验证。

目前源码证据没有显示这些条件成立。若只想获得整洁的下一代实现，优先使用同仓候选目录/入口与独立分支。
