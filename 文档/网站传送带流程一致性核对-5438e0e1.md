# nut-vision-demo 网站传送带流程与提交核对

- 核对日期：2026-11-04
- 对照提交：`5438e0e1f737fc426224f285a4c8b2454d225efc`（`merge: 合并软件粘连漏计修复到LJ-01`）
- 核对范围：网站的机械物料流程、目标视觉计数链路、浏览器教学模型，以及目标提交中的相应实现和验证状态。

## 结论

网站对**目标视觉计数链路的高层描述基本符合提交中的软件路径**：相机帧进入 JPEG-PL 处理，PL 输出 RLE/FRG1 数据，PS 校验并跟踪检测目标，越线后更新计数，再发布同帧 Overlay 信息。

整个机械送料、传送带驱动和接料流程**不是该提交实现的控制功能**。网站自身将机械速度、送料节拍、图像和跟踪标为教学模型或仿真。另有两处硬件路径措辞需要更精确：默认相机路径的 PS 只做有限的 JPEG 预检；默认跟踪按帧号间隔关联，并未启用实际时间基准。

## 核对基准与限制

网站源码位于当前主工作树的 `文档/nut-vision-demo/`，该目录是未跟踪内容，且在指定提交树中不存在。因此本报告比较的是**当前本地网站源码**与指定提交中的实现，不能将网站本身视为该提交交付物。

本报告区分网页展示的目标硬件架构、网页浏览器实际运行的教学仿真，以及提交中可由源码和证据确认的实现。Candidate、仿真和未验收状态按原边界记录，不作为已完成的板端能力。

## 与提交实现基本一致的部分

### 目标视觉计数链

网站描述的目标链路为：

`MJPEG → PS/V4L2 与 DMA → PL JPEG 解码为 Gray8 → ROI/前景处理 → PL RLE + FRG1 → PS 校验、筛选、跟踪与越线计数 → PL Overlay / HDMI`

提交中的相机/硬件请求会分派到 JPEG-PL runner；runner 将 JPEG 交给 `JpegRleDmaTransport`，读取并校验 FRG1 检测记录，调用 tracker，再发布 Overlay 配置。默认计数轴为图像 X 轴、计数线为 `x=320`，方向默认为正向，与网页所述的左向右越线计数相符。

依据：网站 `文档/nut-vision-demo/src/journey.js:3-9`、`src/content.js:85-88, 106-112, 157-168`；提交 `scripts/rle/run_counter.py:147-160`、`scripts/experiments/run_jpeg_counter.py:496-519`、`scripts/rle/jpeg_runtime.py:18-75`、`scripts/rle/jpeg_transport.py:262-350, 375-429`、`scripts/rle/counter.py:26-35`、`scripts/wo0016/stream_counter.py:193-220, 1276-1283`。

### JPEG-PL 与离线 RLE 路径有区分

网站明确说明：默认 JPEG 路径直接消费 PL 的 FRG1 记录，不由 PS 从 RLE 重建区域，也不调用局部粘连拆分；离线或显式 `--software-decode` 路径才走 PS RLE 连通域分析和候选拆分。提交中的 `process_jpeg_frame()` 确实将 FRG1 检测直接传给 `update_detections()`；PS 从游程重建区域的 `update_rle()` 是另一条路径。

依据：网站 `src/journey.js:10-17`、`src/content.js:141-160`；提交 `scripts/rle/jpeg_runtime.py:63-75`、`scripts/wo0016/stream_counter.py:321-365`、`scripts/rle/counter.py:41-112`。

## 逐项差异与边界

### 1. 机械输送流程是模型展示，不是提交中的控制实现

网站展示“直线振动送料槽 → 导流出口 → 主传送带 → 相机区 → 尾端接料盒”，并说明电机可由驱动模块控制。目标提交的软件实现范围是图像采集、PL/PS 图像处理和计数；没有对应的送料振动控制、电机 PWM、传送带速度闭环、机械分料或接料控制代码。

网页的机械运动由浏览器仿真推进：物料根据设定速度改变位置并切换 `bowl/chute/belt/out` 阶段；源码说明物料动画未模拟碰撞，带速没有编码器实测反馈，末端落料也未做碰撞堆积仿真。因此该段可作为 CAD/教学流程说明，不能作为提交已实现的设备控制流程。

依据：网站 `src/content.js:5-8, 13-16, 21-24, 29-32, 61-64`、`src/vision.js:94-109`、`README.md:28`。目标提交相关源代码中未发现机械执行器控制实现。

### 2. 相机 MJPEG 预检没有在 PS 解析完整 JPEG 头

网站 `journey.js` 将 PS 预检概括为检查尺寸和 JPEG 头。提交中的 raw-camera 路径会设置并核对 V4L2 协商结果（`MJPG`、`640×400`），对相机包检查 SOI/EOI 起止标记和最大长度；这一步没有解析完整 JPEG 头来确认基线、采样格式和 DRI 等字段。严格 JPEG 头解析存在于 JPEG 文件夹具预检；相机输入的具体格式还需由 PL 解码路径处理。

建议将网页这一步改述为“PS 核对相机协商格式/分辨率、JPEG 起止标记和长度；PL 解码器继续校验并处理受支持的 JPEG 格式”。

依据：网站 `src/journey.js:3-4`、`src/content.js:37-40, 109-112`；提交 `scripts/rle/jpeg_transport.py:95-113, 128-147`、`scripts/experiments/run_jpeg_counter.py:77-159`。

### 3. 默认 tracker 没有启用实际时间基准

网站部件说明称 FRG1 跟踪使用“实际时间关联”；软件解码分支也称跟踪按实际时间预测。JPEG runner 会记录并传入 `capture_monotonic_ns`，但默认构造 `RleCounter` 时没有设置 `motion_timebase_s`。该值在 `MaskCounter` 中默认为 `None`；未启用时 `_motion_timestamp()` 返回 `None`，关联间隔按帧号差计算。因此“实际时间关联”不符合该提交的默认运行配置。

建议说明为“默认按帧号间隔关联；配置并启用时间基准时才按采集时间计算运动间隔”。

依据：网站 `src/content.js:86, 142`、`src/journey.js:15`；提交 `scripts/experiments/run_jpeg_counter.py:500-519`、`scripts/wo0016/stream_counter.py:193-220, 410-418, 1149-1158`。

### 4. 浏览器教学算法与板端目标路径不同

浏览器模型自己生成合成 Gray8 图像，执行 JavaScript RLE 区域提取；开启拆分时以内部孔洞为种子分配像素，并以简单的正向中线跨越规则计数。板端 JPEG 默认路径则直接读取 PL 的 FRG1 检测记录，不执行 PS RLE 区域重建或局部孔洞拆分；实际 tracker 还包含轨迹确认与迟滞门限。两者的算法步骤和计数门槛不能逐帧等同。

网站已在 README、架构说明和实现边界中标明浏览器运行的是独立 RLE 教学模型，不会运行 JPEG 硬解码、FRG1 硬件或 T7 RTL。这是已声明的演示简化，不应误判为提交源码与网站文案的隐藏冲突。

依据：网站 `src/vision.js:46-67, 69-90, 94-124`、`src/architecture.js:14`、`src/evidence.js:1`、`README.md:28, 32`；提交 `scripts/rle/jpeg_runtime.py:63-75`、`scripts/wo0016/stream_counter.py:197-198, 321-365, 1276-1283`。

### 5. “默认 JPEG-PL”仅指相机/硬件路径

网站多处称“默认 JPEG-PL”。提交中的 `run_counter.py` 若不带参数，CLI 默认模式是 `offline`；相机模式或硬件请求才默认分派至 JPEG-PL runner。因此网页中的“默认”应限定为“默认相机/硬件路径”，不能解释成该 CLI 无参数的默认模式。

依据：网站 `src/journey.js:21`、`src/content.js:37, 85, 141, 157`；提交 `scripts/rle/run_counter.py:147-160`。

### 6. T7 是候选状态，尚不能当作合并提交的整机硬件验收

网页称 T7 为独立候选，并说明候选验证不等于完整有物料装置验收。项目索引记录：JPEG 分支合并进 LJ-01 后，没有对合并后的源码组合重新联合综合、route 或生成匹配 BIT/HWH；已有 T7 报告和 v8 包仍绑定原候选快照。故网页可介绍 T7 候选流程，但不能据此声称该合并提交的硬件组合已经完成整机实现验收。

依据：网站 `src/journey.js:21-23`、`src/architecture.js:14`；提交 `PROJECT_INDEX.md:31`。

## 汇总

| 核对方面 | 结论 |
|---|---|
| JPEG-PL → FRG1 → PS 跟踪计数 → Overlay 的目标软件链 | 高层流程基本一致 |
| 振动送料、电机/传送带控制、机械分料与接料 | 网站教学/机械模型；目标提交无对应控制实现 |
| PS 对相机 JPEG 头的预检描述 | 需要收窄为协商格式/尺寸、标记和长度检查 |
| 默认跟踪使用实际时间的说法 | 与默认代码配置不一致；默认按帧号间隔 |
| 浏览器检测/计数行为与板端算法 | 有意简化，网站已声明教学仿真边界 |
| T7 硬件状态 | 候选；合并源码尚无匹配联合构建/整机验收 |

本核对为只读源码与项目记录检查；未运行测试、未部署板端，也未修改网站源码。
