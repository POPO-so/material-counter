# 网站计数线路展示改进清单

- 记录日期：2026-11-04
- 对照提交：`5438e0e1f737fc426224f285a4c8b2454d225efc`
- 对象：`文档/nut-vision-demo` 网站源码。记录时该目录在主工作区尚未被 Git 跟踪，不属于上述提交。
- 性质：按会话中提出的顺序记录展示改进建议；下列条目不表示已经修改网站或完成现场验收。

网站的传送带与 JPEG-PL 候选链路在流程层面基本对应项目代码，但实体螺母、图像目标、计数事件和显示结果之间的关系仍可讲得更直观。本次提交新增的软件粘连修复也需要与浏览器教学模型区分。

## 1. 把实物流和数据流画成两条并行路线

**当前问题：** 观众看到螺母在传送带上移动，却不容易知道它何时变成图像中的目标，以及后续计数数据从哪里来。

**改动建议：** 在同一视图中并排显示“振动送料槽 → 主传送带 → 相机下方 → 接料盒”和“相机帧 → PL 区域记录 → PS 跟踪计数 → HDMI”。在相机位置连接两条路线，并用同一颜色或编号标识当前讲解的螺母与图像目标。

**完成判据：** 不打开技术详情，也能沿着一颗螺母从送料、成像到计数结果完整追踪。

## 2. 首屏压缩成五个通俗步骤

**当前问题：** 现有逐帧旅程一开始就出现 MJPEG、MM2S、FRG1 等术语，首次观看时需要同时理解物料、图像和接口细节。

**改动建议：** 首屏用“送料、拍摄、找目标、跟踪越线、显示结果”五个主步骤；点击步骤后再展开现有七个技术阶段，保留 PS/PL 职责、协议和验证边界。

**完成判据：** 首屏仅看主步骤就能复述计数过程；技术信息仍可逐层展开。

## 3. 让阶段高亮跟随实际事件

**当前问题：** 网站 `src/main.js` 目前按固定帧数轮换讲解阶段，高亮与螺母位置、检测或越线时刻不直接对应。

**改动建议：** 选定一颗“当前讲解目标”，在它进入视野、产生检测框、获得 ID、穿越计数线、显示结果时推进阶段。暂停、单帧和重置后，高亮应与该目标的当前状态一致；没有目标时显示等待状态。

**完成判据：** 阶段高亮由对应事件触发，不再仅由经过的帧数驱动。

## 4. 突出“为什么加一”

**当前问题：** 累计数字可以看到，但“同一 ID 首次沿指定方向越线才加一”的判定过程不够显眼。

**改动建议：** 用一颗示例螺母展示连续状态：`ID 07 在线左侧，累计 3` → `首次左到右越线，累计 4` → `继续运动，累计仍为 4`。同步突出计数线、目标轨迹、已计数标志和本次 `+1` 事件；并行越线时分别标明每个 ID 的事件。

**完成判据：** 观众能指出哪一帧触发加一，并理解后续帧为什么不会对同一 ID 再次加一。

## 5. 把计数和显示分支分开

**当前问题：** 连续的流程箭头容易使人以为 HDMI 画面显示完成后才产生计数。

**改动建议：** 明确绘制 PS 越线判定与累计数更新，以及二值视频和 PS 元数据送往 PL Overlay 的显示分支；在汇合处标出同帧身份。说明显示侧忙时可以跳过新显示帧，计数仍继续。

**完成判据：** 图中能清楚区分“计数事件发生”和“结果显示”，且不会把显示帧率当作计数吞吐。

## 6. 在画面旁直接标注仿真边界

**当前问题：** README 已说明网站不连接板卡，但灰度图、RLE 图和 30 FPS 与候选硬件讲解放在同一画面，容易被误读为板端实时输出。

**改动建议：** 在图像面板和性能数字旁常显“浏览器合成 Gray8 / RLE 教学模型”“30 FPS 仿真节拍”。JPEG-PL、FRG1 和 T7 的说明另标为候选硬件链路；不要把浏览器像素处理动画呈现为硬件执行记录。

**完成判据：** 截取任意单张网页画面，仍能看出哪些是浏览器模拟、哪些是候选硬件流程。

## 7. 用粘连案例解释默认 JPEG 与软件 RLE 两条路径的差别

**当前问题：** 两颗螺母形成一个区域时，观众不容易看出默认 JPEG/FRG1 路径与软件 RLE 路径各自做了什么。浏览器模型仅以简化孔心规则处理 2–3 个目标，不能代表本次提交的粘连修复。

**改动建议：** 用同一粘连案例分别展示原始区域、候选分离结果、目标 ID 与计数变化。明确默认 JPEG/FRG1 入口直接使用 FRG1 检测，不运行本地 RLE 拆分；软件 RLE 路径可介绍本次提交新增的有界多螺母拆分、超限父块先拆分再拒绝、父团越线后有限恢复，以及证据不足时保留歧义。浏览器交互继续标为简化模型，不暗示已经复现或验收这些算法。

**完成判据：** 两条路径的实际职责和模拟范围可辨；页面不把软件修复写成默认 JPEG 路径已启用，也不宣称真实物料准确率已验收。

## 8. 给验证状态加简短标识

**当前问题：** 源码能力、独立候选板测与完整装置验收放在一处时，读者需要读完长段文字才能判断证据覆盖范围。

**改动建议：** 在相应步骤旁使用“源码已有”“独立候选板测”“真实物料待验收”等短标签。把 11.31 FPS 标为独立候选的空场景板测，把 30 FPS 标为浏览器仿真节拍；项目方提供的 P12-R4 数字标为参考基线。T7 继续标成候选，因为合并后的源码组合尚无匹配的新 BIT/HWH 与完整硬件验收。

**完成判据：** 读者不查长篇证据说明，也能分辨已实现代码、候选验证和未完成验收。

优先处理第 1、3、4 项：它们直接解决“看到螺母运动，却不知道何时计数”的理解障碍。其余条目按上列原顺序推进。

核对依据：`docs/00_scope.md` 的机械与编码器状态、`scripts/rle/run_counter.py` 与 `scripts/rle/jpeg_runtime.py` 的 JPEG 候选入口、`docs/superpowers/plans/2026-11-03-software-cluster-undercount.md` 的软件修复及未完成验收、`PROJECT_INDEX.md` 的 JPEG/T7 合并和板测边界。上述来源在目标提交中；网站目录仍须作为独立源码核对。
