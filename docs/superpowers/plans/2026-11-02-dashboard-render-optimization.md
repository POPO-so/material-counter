# 仪表盘渲染优化实施计划

> **For agentic workers:** 按两个有序阶段实施；每阶段先写/更新测试，运行该阶段测试，再提交。不要部署板端。

**Goal:** 降低 `DashboardComposer` 面板更新与共享输出帧绘制开销，同时逐像素保持完整有效输出。

**Architecture:** 第一步以屏幕显示值构造缓存 key，加入命中率计数并把低层诊断折叠到现有 BTN3 PS/丢帧详情。第二步持久化静态 chrome，并按三个共享输出槽的版本延迟同步；每帧仍完整生成动态预览、叠加和身份标记。

**Tech Stack:** Python、NumPy、Pillow、OpenCV、multiprocessing 共享帧槽、pytest。

**Spec:** [仪表盘渲染优化设计](../specs/2026-11-02-dashboard-render-optimization-design.md)

## Global Constraints

- 保持 1280×720 输出尺寸、现有计数/跟踪/阈值/控制行为、PL/HDMI 接口不变。
- 不改遥测采样周期，不部署板端、不重启服务。
- 所有输出槽完整有效；帧标记与每帧动态预览按现有语义更新。
- 仅改本任务相关源码、测试及项目树文档；不触碰根工作区已有修改。

## Review Focus

- 显示值舍入边界、无效值与 unknown：key 命中时画面必须与上次相同；显示值变化必须更新。
- 三个输出槽首次写入和复用：必须先同步正确 chrome，不能残留未初始化或旧面板像素。
- 面板 key 更新后尚未轮到的槽：该槽下次使用时必须追上当前版本。
- PL 预览、二值预览、计数线、检测框、跟踪文字和帧标记必须保留既有像素行为。
- BTN3 页切换需显示对应 PL/PS 遥测；总览保留现场关键计数和状态字段。

## 遥测回放发现与补充优化（2026-11-02）

- 回放发现检测目标数量仍在静态面板 key 中：保存的 201 帧 trace 中目标数变化 67 次，静态 key 命中率只有 66.2%。将检测数量改为独立的小区域更新后，同一 trace 命中率为 99.5%，数字仍随检测框数量更新。
- 固定目标数回放最近 200 个板端遥测窗口时，原静态 key 命中率为 0/200：CPU、FPS、丢帧等低频值仍令整张 chrome 失效。现将显示精度归一化后的动态遥测值按槽位缓存，只在各自动态区域变化时恢复并重绘局部区域；同一回放的静态 key 命中率为 199/200（99.5%）。
- 性能剖析发现 `_wrap_gutter` 每加入一个字符都会重新测量整行前缀，混合文字换行的宽度累计为 O(n²)。改为逐字符累计宽度，并保存每行的前缀宽度供省略号截断复用。
- 线性测量回归测试通过；另用旧实现和新实现对 2500 组固定随机种子的混合中英文、宽度、字号和行数输入做结果对比，输出完全一致（0 差异）。子代理只读边界审查未发现行为差异；仅指出理论上浮点舍入差异可能影响恰落在宽度边界的字符，当前 Pillow 字体未复现。
- 最近 200 个保存遥测窗口，以真实 `dashboard_values` 和运行诊断生成面板，循环复用 3 个输出槽；每轮先预热 10 帧，余下 190 帧计时，4 轮交替新旧换行实现。旧实现 draw_ms mean/p50/p95 为 28.35/28.20/35.08 ms；新实现为 8.13/8.01/11.04 ms，mean 降低 71.3%。这是 Windows 主机上的局部 A/B，不能代替板端 draw_ms。
- 最新相关本地测试合计 127 passed、8 failed。`test_compositor.py` 为 74 passed、3 failed（1 项既有字体测量缓存断言、2 项旧 viewport 尺寸断言）；`test_integrated_run.py` 为 53 passed、5 failed（既有详情页返回类型、预览默认值、2 项旧 viewport 坐标、未初始化相机对象断言），均与仓库已有基线问题一致。`git diff --check` 通过。
- 未部署或重启板端；300–600 ms 的板端目标尚未实测，需由 Manager 按另行安排在板端验证。

## ASCII 动态文本字形缓存（2026-11-02）

- DashboardComposer 的 ASCII 动态值原先在完整文本缓存未命中时逐字符调用 Pillow；现按字号、字符和 1/64 像素相位缓存字形遮罩，仍逐字符按原布局合成，另缓存热路径字号 12/20 的 ASCII 字符 advance。整串 RAQM 绘制经板端 Pillow 检查会产生像素差异，因此没有采用。
- TDD 像素测试：Windows 本机 Pillow BASIC 下 128/129 个重复数字文本与旧逐字符输出逐像素一致；完整 compositor 用例 76 passed、2 failed。两项失败均为已有的旧视口尺寸断言（期望 512×320，当前实现为 460×288）。
- 板端 Pillow 9.0.1 / RAQM 内存核验：7 种实际样式/数字文本 × 12、20px 共 14 组，字形缓存结果与旧逐字符结果 0 像素差异。对 5 条动态遥测文本做 25 轮光栅化微基准，旧路径 9.005 s，字形缓存路径 1.234 s，快 7.3×；这是文本子路径微基准，不代表板端整帧 draw_ms。没有写板端文件或更改服务状态。
- 完整本地 draw_ms A/B：旧版 `f7ce183` 与当前版以相同的 210 帧合成负载交替运行 4 轮，每轮预热 20 帧、统计 190 帧，3 个输出槽轮转并启用 PL 预览。旧版 mean/p50/p95 为 8.265/8.202/9.272 ms；当前版为 1.889/1.828/2.324 ms，mean 下降 77.1%，两版 key 命中率均为 99.52%。输入为 Windows 主机上的合成遥测，不是板端运行测量。
- 未部署；板端完整 draw_ms 和 E2E 的优化后数值仍需后续部署验收，不能据本地或文本微基准认定已达到 300–600 ms 目标。

## 共享输出帧直接绘制（2026-11-02）

- 板端目标环境 profiling 中，5 个动态区域每帧分别构造 PIL 区域图并回拷，合计约 110 ms。改为 `Image.frombuffer` 直接映射完整 1280×720 输出数组后，在对应区域先恢复静态 chrome，再原位绘制；省去每个区域的 PIL 拷贝与回拷。VideoPump 仍收到完整有效帧。
- TDD 回归测试使用真正的 `multiprocessing.shared_memory` 缓冲，检查没有非连续区域 `Image.fromarray` 物化，并与旧区域复制参考输出逐像素比较。定向测试通过；完整 `test_compositor.py` 为 77 passed、2 failed，失败仍是仓库既有的旧视口尺寸断言（期望 512×320，实际 460×288）。
- 板端 Pillow 9.0.1 / RAQM 内存 A/B 使用 3 个共享内存帧槽、动态遥测文本、检测框和轨迹，50 帧（10 帧预热、40 帧计时）：旧区域复制路径 mean/p50/p95 为 109.254/108.129/112.563 ms；直接缓冲路径为 81.370/80.214/84.239 ms，mean 下降 25.5%，0 帧/像素不一致。没有写板端文件、启动或停止服务。
- 与板端原部署源码提交 `ddd5174d` 的同负载完整 compositor 回放相比，当前代码 mean/p50/p95 为 80.914/80.075/83.898 ms；部署源码为 404.543/402.900/409.153 ms，mean 降约 80%。这是目标板 CPU 上的内存回放，没有主循环同时运行；不能代表实际并发负载下的 draw_ms，也不能代表 E2E。
