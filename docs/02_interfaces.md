## 当前运行实现：GRAY8_PACKET_V1（已授权，板端验收待完成）

此节记录当前代码实际使用的 Gray8 DMA 协议，不代表正式接口已签核：

- 输入为 320×240 Gray8，一像素一字节；raw MJPEG 直接解码为 Gray8，不复制 RGB，也无 RGB 回退。
- MM2S TX 长度为 **76,832 字节**。16 字节小端头含 `0x47525938`、`(H<<16)|W`、payload 长度和 frame ID；其后是 Gray8 payload；16 字节小端尾含 `0x454e4438`、frame ID、payload sum 和 `0xc0dec018`。
- 旧 `WO14` 格式（`0x574F3134` / `0x454E4434` / `0xC0DEC014`）不再作为活动协议；历史 320×240 测试与结果保留，见 [ADR-0006](adr/adr-0006-gray8-active-protocol.md)。
- S2MM 输出为 320×240 Binary8，**76,800 字节**。PL threshold 生成掩膜，PS 逐像素校验后复用 MaskCounter。
- Gray8 adapter、320×240 wrapper、S2MM guards 的 XSim 已通过；新 BIT 已加载，3/3 合成帧已在板端 DMA 并通过 Binary8 全像素校验。真实相机测试因板卡只枚举 USB root hub、未出现 `/dev/video*`，在 DMA 前失败且未留置 buffers。合成帧结果不作为帧率或准确率结论；当前没有 Gray8 性能或 YOLO 收益数据。
- 旧 RGB RTL、编码、构建及回放代码已从当前实现移除；历史报告仍保留原结果，不能充当 Gray8 板测证据。

详情见 [ADR-0004](adr/adr-0004-gray8-dma-input.md)、[Gray8 运行说明](../scripts/gray8/README.md) 和 [实施状态](../PLAN.md)。

## 接口 A · 视频流（历史设计基线；当前实现已改为 Gray8 packet）

| 信号 | 宽度 | 含义 |
|---|---|---|
| TDATA | 24 bit (RGB888) | 源侧像素格式 |
| TUSER[0] | 1 | SOF（帧首） |
| TLAST | 1 | 行末 |
| TVALID / TREADY | 1 / 1 | **必须严格实现反压** |

- 处理分辨率：**320×240 @ ≥30fps**（第一版，`[Target]`）；640×480 作为 stretch
- 像素时钟：100 MHz

> **★ 像素格式约定**：源接口按 **RGB888** 定义；**PL 内部第一级（rgb2gray）的输出即 Gray8**。
> 24 bit 只在源到 rgb2gray 之间这一小段存在。这决定压缩比公式中 `bytes_per_pixel` 取 3 还是 1
> —— **两个数都算，答辩给 Gray8 基准（保守、诚实）**。
>
> **待定**：具体的源侧接口参数取决于 C2（HDMI IN）与 C3（引脚预算）的实测结论。

## 接口 B · 特征记录流（PL → PS，经 AXI DMA S2MM）

**★ 字段集按两条 Route 的超集定义** —— Route 切换不得触发接口变更（那是付费动作）。

| 字段 | 位宽 | 含义 | Route A | Route B |
|---|---|---|---|---|
| `x_min` | 10 | 段/区域起始列 | 使用 | 使用 |
| `x_max` | 10 | 段/区域结束列 | 使用 | 使用 |
| `centroid_x` | 10 | 质心列 | 可由 x_min/x_max 导出 | 使用 |
| `area` | 16 | 前景像素总数 | 使用 | 使用 |
| `peak` | 8 | 列投影峰值 | 使用 | 填 0 |
| `row_min` | 8 | 纵向最小行 | 填 0 | 使用 |
| `row_max` | 8 | 纵向最大行 | 填 0 | 使用 |
| `centroid_y` | 8 | 质心行 | 填 0 | 使用 |
| `flags` | 8 | bit0=疑似合并（宽度超阈值）；bit1=触边；**bit2=本记录含二维字段** | | |

**帧尾元数据**（与记录分开的固定位置，用于原子校验）：

| 字段 | 位宽 | 含义 |
|---|---|---|
| `frame_id` | 32 | 帧序号，单调递增 |
| `timestamp` | 32 | PL 侧像素时钟计数 |
| `total_fg` | 32 | 全帧前景像素数 |
| `seg_count` | 8 | 本帧记录数 |
| `flags` | 8 | bit0=溢出（记录数超上限） |

### ★ 原子性规则（PS 强制校验）

> **PS 只有在「帧尾元数据中的 `frame_id` 与 `seg_count` 与收到的记录数一致」时才接受该帧；
> 否则丢弃并计入 `frame_drop` 计数器。**
>
> 这条规则是防止「随机 ±1 计数错误」的唯一有效手段。初学者极易踩的坑：
> 这帧的记录被算进下一帧 → 计数随机 ±1 → 极难复现和定位。

## 接口 D · 编码器带速（Planned，尚未实现）

编码器用于获取**单条可调速主输送带的实际运行速度**，作为 PS 侧运动状态和后续送料控制的正式速度输入。当前仓库尚未包含编码器硬件、PL 计数器、驱动或标定实现，因此以下是接口预留，不是已完成接口。

目标数据路径：

```text
encoder pulse/count input → PL/PS capture and counter → calibration → encoder_speed → PS tracking/counting/control
```

| 逻辑字段/信号 | 当前状态 | 说明 |
|---|---|---|
| `encoder_speed` | **Planned** | 标定后的实际带速；单位、缩放和位宽待编码器型号与采样周期确定 |
| `encoder_valid` | **Planned** | 当前速度样本是否有效；失效行为待硬件接口确定 |
| `encoder_timestamp` | **Planned** | 速度样本对应的时间基准；不得与现有 `frame_id` 或 `timestamp` 混用 |

这些字段暂不加入接口 B 的特征记录固定布局，以免在实现证据不足时改动已冻结的 PL→PS 记录契约。视觉位移速度可以作为诊断或预测量，但不能冒充已实现的编码器实际带速。
